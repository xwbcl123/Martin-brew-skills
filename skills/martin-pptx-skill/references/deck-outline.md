# Content + visual Deck Outline

Use for new decks or material narrative/visual changes, through the host /deck-outline command or directly when no command exists. Both entry points share this reference. Reuse existing content, sources, template and approvals; complete only missing decisions. Do not generate a second outline for asset production or a narrow text correction.

Deck level: audience, goal, central message, narrative arc, language, slide/time budget, source/disclosure boundaries and selected template/Design/Style. Keep the requested total page count. Source facts, inference and uncertainty remain distinct.

Each slide specifies:
- ID, purpose, suitable title, supporting facts with source locations, speaker points and any decision request. Use an action claim only when appropriate; a topic title can be clearer.
- Visual form/subtype and the relationship it explains. Corporate decks need deliberate visual communication; avoid default walls of bullets. Text-only pages can be intentional when justified by communication needs.
- Composition and reading order, image regions, native labels with component anchors, exact embedded text when selected, required editable data/objects, planned assets and acceptance conditions.

Bind the existing template/Design/Style and the separate production `visual-contract.json` defined in [verification](verification.md). The design rationale can live in an existing Design.md or named outline section; do not duplicate writable facts. Required production fields, not document count, determine completeness.

Review content and materially new visual decisions together. Reuse current user approval, including explicit corrections. Asset inspection is agent QA, not a per-image user permission gate. Save the outline revision/approval reference through the host's task convention. An approved outline alone does not prove actual assets, editable notes or final rendering exist.
