# Explicitly requested temporary tunnel preview

- Discover capabilities directly with `cf tunnels quick-start --help` and `cf tunnels --help`. Root help and `command -v cloudflared` are incomplete discovery signals: cf can manage/download its own cloudflared engine. Do not conclude a separate installation is needed merely because cloudflared is absent from PATH. Do not use cf Pages as a substitute when the user asks for a tunnel.
- `cf tunnels quick-start http://127.0.0.1:<port>` creates a temporary trycloudflare.com URL; it stays live while the cf process runs. No DNS change, named tunnel, Pages project/deployment, launchd service, OAuth change, or formal publishing approval is required. Explain that anyone with the URL can access it, and that noindex is not authentication. Never generalize one preview authorization to other content.
- Bind preview to the explicit run/revision and verify the frozen article and assets. Read `.automation/blog-e2e/preview.json` and inspect actual rendered paths; Hexo permalink can include the dated filename even when a slug exists. Do not guess the path or use unrelated latest output. An existing valid isolated preview can be reused; stale/missing build output must be rebuilt in a scoped disposable workspace, not copied blindly.
- Expose only a derivative single-article snapshot, referenced browser images and required theme CSS/JS/fonts/images. No vault root, admin directory, Git files, source Markdown, logs, provenance sidecars, or directory listings. Exclude theme source HTML and source maps. Include dynamic theme assets such as `/img/loading.gif` and the favicon; checking only static src/href references misses them.
- Add robots noindex/nofollow/noarchive and robots.txt Disallow to the derivative snapshot, not the frozen article. Root may redirect to the exact article. Preserve formal article/asset digest unchanged.
- Run the local server and cf tunnel as tracked background terminal processes, retaining both session IDs and PID/port. For an explicitly shared ongoing preview, persist the processes across session release; do not create a recurring job. Store run/revision, digest, scoped snapshot path, exact URL, verification and shutdown handles in the run ledger, never credentials.
- Verify local HTML first, then fetch the public URL and every displayed WebP (cover/banner included) and compare bytes/hashes. Confirm sensitive paths return 404. Use browser mobile emulation to check viewport overflow and scroll all sections so Fluid lazy-loading resolves before judging image visibility. A blank unvisited lazy-load placeholder is not proof the image endpoint failed. Before diagnosing a lazy-load bug, call `Page.bringToFront`, confirm `document.visibilityState === 'visible'` and focus, then scroll the actual image into view and inspect currentSrc/naturalWidth; background tabs can pause IntersectionObserver callbacks even while screenshots and DOM reads work. Do not count a successfully decoded loading.gif as the real image merely because complete/naturalWidth are nonzero. If Fluid lazy-loading remains unreliable in the preview, replace `srcset="/img/loading.gif" lazyload` with `loading="eager"` only in the derivative HTML and verify every body image's currentSrc/naturalWidth after a fresh public load. Do not alter frozen Markdown or claim formal production lazy-loading is fixed.
- Update an existing authorized preview in place for revisions of the same article rather than creating a new tunnel each time. Copy the new verified assets first and atomically replace the rendered article last, so readers never encounter HTML pointing to missing new files. Add a revision query parameter to the delivered URL and update the run ledger with the new article hash/digest. A request to replace a different article's preview is a lifecycle transition: close the explicitly superseded tunnel/server using the procedure below, then create and verify a newly scoped snapshot; do not silently expose both articles under the old grant.
- On a tunnel connectivity warning, test both the loopback article and the public article before restarting or changing network settings; log noise alone does not establish service loss. Preserve a healthy shared URL and do not disconnect VPN merely because the tunnel emitted an error.
- Distinguish tunnel/readback from formal publication. Deliver the clickable URL first, then a short scope/lifetime and verification note; keep process IDs and technical traces in the ledger. Keep an authorized shared preview alive across session release and do not close it merely because the article was published.

## Replace or retire a shared preview

1. Read the exact run's preview ledger and identify its cf process, owned loopback server, port and public article URL. Bind closure to the actual user request; do not infer that review completion or publication elsewhere authorizes stopping unrelated previews.
2. Stop both tracked processes with `process_manage(action='kill', session_id=...)`; these independent stops may run in parallel. If a handle is stale, verify the live process command and bound origin before using a PID. Do not use a broad process-name kill or delete Cloudflare DNS/account resources: a quick tunnel's exposure ends with its owning process.
3. Verify the old loopback port no longer accepts connections before reusing it for another server. Request the old public URL with a fresh query and check that the article is no longer served. A Cloudflare tunnel error, non-200 response or DNS failure can be the expected retired state; do not require HTTP404. Pair remote evidence with the stopped processes and closed port, because an access-denied response alone does not prove shutdown.
4. Distinguish preview failure from production availability. If an HTTP client returns an access interstitial for the formal article, use a real browser, check the navigation response status and a distinctive body passage, and preserve both observations. Do not consult an archived copy to prove a live service is up or a tunnel is retired. Associate delayed connection-termination logs with their originating process and shutdown time rather than diagnosing the replacement tunnel from an old log.
5. Update the preview ledger with closure time, request provenance, stopped handles and local/remote readback; retain previous successful preview evidence. Record review acceptance separately, preserve the published article/digest, and keep an exact audit record with verified additive backup. For a replacement, start the new scoped server/tunnel only after the old closure is established, then run the normal public/mobile verification before delivering the new link.

## Rebuild an unpublished article without touching production

1. Verify the exact frozen source hash and selected assets. Create a disposable build workspace under the approved scratch root; copy the site's package metadata, Hexo/Fluid configuration and Fluid theme, but no unrelated posts, repository metadata or credentials.
2. Reuse the site's existing installed dependencies, for example by symlinking its `node_modules`. Place only the bound article and its browser images in the disposable `source/`. Disable analytics, comments, search and navigation to absent pages in the preview configuration. Treat every configuration change as preview-only.
3. For production parity, first record an explicit publishable candidate (`published: true`) before freeze/approval, and copy those exact bytes into the disposable site. Run the existing local Hexo entry point with `generate --force --bail`; run `render-check --run R --site-dir <isolated-site>` afterwards. If only an editorial draft derivative is authorized, a temporary false-to-true override can render it, but record the delta and label it editorial-only: it must not satisfy readiness or bypass the exact-source checker. Metadata changes never grant public distribution approval.
4. Locate the actual generated article path and assert that current illustration filenames and expected body text are present and Hexo tags are fully rendered. Copy only that page and the required browser resource directories into the isolated serving snapshot; do not expose generated archives, search indexes, other content, source originals or provenance JSON.
5. Apply noindex and any preview-only eager-loading fix to the snapshot, copy assets before the page, and verify the frozen source hash remains unchanged. Recheck public image bytes, blocked paths and mobile viewport overflow before reporting the new preview as ready.
